# Deploy the L&D demonstration

Target: Vercel, using the Next.js preset and Node.js 24.x. The repository includes `vercel.json` for reproducible install/build commands. Employee records are read from a Supabase Postgres `employees` table (Story 1.1), so every environment needs the Supabase variables below.

## One shared Supabase project

Local development, Vercel Previews, the demo and CI all use **one shared hosted Supabase project** (free-plan limit). That is acceptable only while all data is fictional:

- Anything written to it (a migration, a seed, a test row) is immediately visible to every environment, including the live demo.
- Additive migrations (for example a new table the deployed code does not read yet) may be applied during development. Changing or destructive migrations are applied only after their PR is approved.
- The RLS integration tests create and delete their own throwaway auth users and `BS-99xx` rows; they never touch the seeded demo employees.
- **Before any real employee data is loaded, production must move to its own Supabase project.**

`DEMO_ADMIN_EMAIL` and `DEMO_ADMIN_PASSWORD` (Story 1.2), and `DEMO_SESSION_SECRET` and `DEMO_STAFF_PASSWORD` (Story 1.3), are retired: delete them from Vercel and `.env.local`. The old `manager@example.com` credentials and the shared staff password are rejected.

Store these in Vercel's environment settings and `.env.local` (git-ignored), never in repository files or `vercel.json`. In GitHub, set the three Supabase values as repository secrets (`gh secret set NAME < value-file`, or the repository settings page); CI passes them to both jobs. Pull requests from forks do not receive secrets, so their RLS and live accounts tests are skipped, and their whole e2e job fails: e2e global setup throws without `SUPABASE_SERVICE_ROLE_KEY` because it cannot create the throwaway Administrator.

## Administrator accounts (Story 1.2)

Administrators sign in with a named Supabase Auth account (email + password). The session is the Supabase auth cookie, refreshed by `src/middleware.ts`, and lasts at most 8 hours from sign-in. The `admin` role comes from the user's `app_metadata.role`, which only the service role can set. Employee reads use a per-request client carrying the user's JWT, so the RLS policies are the enforced rule.

There is no self-registration. One-time setup for the shared project:

1. **Disable sign-ups (manual).** In the Supabase dashboard, open Authentication → Sign In / Providers and turn off **Allow new users to sign up**. (`supabase/config.toml` sets `enable_signup = false` to document this, but the hosted project setting is changed by hand.)
2. **Seed the first Administrator.** Put `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` (at least 12 characters) in `.env.local` and run `npm run db:seed-admin`. It creates the account through `accounts-store.create()`, prints only the email, and refuses to run (exit code 1, nothing created) if any Administrator already exists. Remove both variables from `.env.local` afterwards.

Further accounts are provisioned by an Administrator in the app (Story 1.3). Tests and e2e create and delete their own throwaway Administrators (`e2e-admin-*@example.test`, `accounts-test-*@example.test`), so they never need a real Administrator's password.

## Staff accounts (Story 1.3)

An Administrator opens an employee's profile and, on the Overview tab's **Sign-in account** panel, types an initial password (12 to 72 characters, meeting the project's password policy) twice and selects **Create Staff account**. The server action checks the Administrator session first, then calls `accounts-store.create()` with the service-role client, which:

- creates a confirmed Supabase Auth user with the employee's own primary email (never typed into the form) and `app_metadata: { role: "staff", employee_id: "BS-nnnn" }`;
- links `employees.auth_user_id` only if the row is still unlinked, deleting the new user if that link fails or loses a race;
- refuses an employee who already has an account, before creating anything.

There is no invite or magic-link email (the shared project has no SMTP): the Administrator passes the initial password on outside the app. Staff sign in with their employee email; the session lasts at most 12 hours, and their own employee row is read through RLS (`employees_select_own`). At runtime the service-role key is used only by this Administrator-only provisioning action. There is no in-app password reset yet: to reset a Staff password (for example after a mistyped initial password), someone with access to the Supabase dashboard (service role) opens Authentication → Users → the user and resets or sets a new password.

**Demo Staff account.** Put `SEED_DEMO_STAFF_EMAIL` (a seeded employee's email, e.g. one from `npm run db:seed`) and `SEED_DEMO_STAFF_PASSWORD` (at least 12 characters) in `.env.local` and run `npm run db:seed-demo-staff`. It creates and links the account through `accounts-store.create()` and prints only the email. If that employee already has an account it exits 0 and creates nothing; missing or short variables exit non-zero naming the variable.

e2e global setup inserts throwaway employees (`BS-98nn`, team/title `E2E Throwaway`, emails `e2e-staff-<run>-<n>@example.test`), links five of them to throwaway Staff users through the service role (one is archived and restored by the archive spec, one is made a manager by the department-manager spec, and one is archived and restored by that manager in the manager-archive spec), and leaves two without an account (one for the provisioning spec). Teardown deletes them; setup first sweeps leftovers of an aborted run.

## Database migrations and seed

Migrations are forward-only SQL files in `supabase/migrations/`, applied with the Supabase CLI pinned in `devDependencies`.

```sh
npm run db:push   # applies pending migrations to the database in SUPABASE_DB_URL
npm run db:seed-admin   # one-time, BEFORE db:seed: creates the first Administrator (see above)
npm run db:seed   # idempotently inserts the L&D and Central R&D departments, sets L&D's manager to the Administrator (only while it has none), upserts the 8 fictional employees' basic details, places fixture employees with no department in Central R&D, inserts their missing external interviews, completed training, LMS stub enrolments, (Story 7.4) skills assessments and evaluations, and (Story 4.5) one open assignment per fixture employee that has none open
npm run db:seed-demo-staff   # optional: creates the demo Staff account (see above)
```

- `db:push` reads `SUPABASE_DB_URL` from the environment or `.env.local` and never prints it.
- `20261008000000_archive_and_audit.sql` (Story 1.4) is additive: it adds `employees.archived_at`, the append-only `audit_events` table and the `set_employee_archived` function. The Story 1.4 code reads `archived_at` on every Administrator directory load and every Staff request, so apply this migration before deploying that code; otherwise the directory reports "Employee records are unavailable" and Staff sessions end. `audit_events` rows cannot be updated or deleted by any API role, the service role included; live tests and e2e leave audit rows for their throwaway `BS-98nn`/`BS-99nn` ids behind by design.
- `db:seed` reads `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` the same way and upserts employees by Employee ID, so it is safe to rerun. Migrations never seed data. For interviews, training and LMS stub enrolments it is insert-only by deterministic ids (`interviewSeedId`, `trainingSeedId`, `lmsStubSeedId`): existing rows are never updated, so staff edits and withdrawals of seeded demo interviews survive a re-run. Completed training (`progress` 100) goes into `training_history`; in-progress entries go only into `lms_stub_enrolments` (`status` `in_progress`, `synced_at` = insert time), never into `training_history`. Because re-seeding does not refresh `synced_at`, seeded stub data shows as "Stale … as of" once it is more than 24 hours old, which is truthful.
- Data sources: interviews are read only from `external_interviews` (through `interviews-store`); training only through `training-store` (completed entries from `training_history`; current enrolments from the LMS adapter `lms-client`, a stub over `lms_stub_enrolments` until real LMS access exists). Nothing reads the fixture for training at runtime. Skills and the evaluation are read only from `employee_skills` and `employee_evaluations` (through `assessments-store`, Story 7.4). Employment history is read only from `employment_history` (Story 7.3, through `employment-history-store`). Current work is read only from `assignments` (through `assignments-store`, Story 4.5). Other nested profile data (the attendance summary) still comes from `src/data/employees.ts` through `employees-store`.
- Departments (Story 4.1): `db:seed` needs `20261014000000_departments.sql` applied first. It inserts L&D (top level) and Central R&D (under L&D) by fixed ids, insert-only, so later renames or re-parents survive a re-run, and sets `department_id` to Central R&D only for fixture employees whose `department_id` is null. Administrator directory reads select `employees.department_id`, so apply this migration before deploying the Story 4.1 code.
- Department managers (Story 4.2): `20261014010000_department_managers.sql` adds `departments.manager_user_id` (an auth user id; null = no manager), its index and the `departments_select_managed` policy (a user reads the departments they manage). Run `npm run db:seed-admin` before `npm run db:seed`: the seed sets L&D's manager to the Administrator account — the user whose email is `SEED_ADMIN_EMAIL` when that is set, else the earliest-created Administrator — only while L&D has no manager. With no Administrator yet it prints a warning to run `db:seed-admin` first and carries on; re-run `db:seed` afterwards. Central R&D gets no manager. Administrator department reads select `manager_user_id`, so apply this migration before deploying the Story 4.2 code. A Staff account that manages at least one department gets the management portal (role `manager`, derived on every request; session length stays 12 hours); an Administrator stays `admin`. An Administrator assigns or removes managers in **Departments → Set manager**; the person must already have a sign-in account.
- Manager scoping (Story 4.3): `20261014020000_manager_scope.sql` adds the `manages_department(uuid)` / `manages_employee(text)` SECURITY DEFINER helpers (execute for `authenticated` only) and select-only policies so a department manager reads the departments in their subtree (the ones they manage and every sub-department), the employees in them, and those employees' attendance, training history and LMS enrolments. No write policy is added, and interviews get no manager policy. The app re-derives the same scope at the store on every request (`src/server/manager-scope.ts`). Until it is applied, a manager's scope covers only the departments they manage directly (sub-departments are not visible), and their directory lists only the employees RLS lets them read in those departments, which is at most their own record and only when it sits in one of them; Administrators and Staff are unaffected.
- Assignments (Story 4.5): `20261014030000_assignments.sql` adds the `assignments` table (client, project, role, allocation, start date, latest-update note, status `open`/`closed`, completion date, department), the `assignments_one_open_per_employee` partial unique index, the `assignments_guard` trigger (copies the employee's department on insert and refuses employees without one; locks every identifying field; only the note may change while open, and the only status change is open → closed with a completion date on or after the start date; closed rows are frozen) and an `assignments_no_delete` trigger, both binding the service role too, plus RLS: Administrator, managed (`manages_employee`) and own-row select; insert and update for the Administrator or a manager over the employee's department; no delete policy. Apply it, **then** run `npm run db:seed`: the seed inserts each fixture employee's former "current work" as an open assignment (fixed id `assignmentSeedId`, client "Not recorded", start date from the work period, else the join date), insert-only, after placing employees in Central R&D, and skips employees who already have an open assignment. The fixture's Git commit counts are not migrated and the "Recorded Git activity" panel is gone. Every employee read (Administrator, manager and Staff) reads assignments, so until this migration is applied those reads show "employee records unavailable". Test rows can never be deleted (by design), so the live RLS test and the e2e spec reuse fixed throwaway employees and departments (BS-91xx, "RLS Assign slot …", BS-9190, "E2E Assignments") and only close their assignments.
- Assignment evaluations (Story 4.6): `20261016000000_assignment_evaluations.sql` adds the `assignment_evaluations` table (one per closed assignment: evaluation text, optional client feedback, the assignment's employee and department, `created_by`/`created_at` for the first writer and `authored_by`/`updated_at` for the latest, each with a name/role snapshot `*_by_name`/`*_by_role` taken from the JWT on every write; `employee_id` and `department_id` reference `employees` and `departments`, on delete restrict), the indexes `assignment_evaluations_employee_id_idx` and `assignment_evaluations_department_id_idx`, the `assignment_evaluations_one_per_assignment` unique index, a new, additive `assignments_select_department_managed` select policy on `assignments` (the assignment's own department manager can still read it after a transfer; no existing policy changes, and until Story 4.8 adds transfers this path is reachable only through the database and the store), the `assignment_evaluations_guard` trigger (refuses an assignment that is missing or not closed; copies the employee and department from the assignment; takes the authors from the JWT; locks the identifying fields) and an `assignment_evaluations_no_delete` trigger, both binding the service role too, plus RLS: select for the Administrator, a manager over the assignment's department (`manages_department`) or over the employee (`manages_employee`), and the employee themselves; insert and update for the Administrator or a manager over the assignment's department, never on an assignment of the writer's own linked employee (Story 4.10); no delete policy. No seed change. Every employee read (Administrator, manager and Staff) reads evaluations, so until this migration is applied those reads show "employee records unavailable". Test rows can never be deleted (by design), so the live RLS test and the e2e spec reuse fixed throwaway employees and departments (BS-9130..BS-9153, "RLS Eval slot …", BS-9191, "E2E Evaluations") and only close their assignments.
- Backfilled projects (Story 4.7): `20261016010000_backfilled_projects.sql` adds the `backfilled_projects` table (an employee's self-reported past project: department from the list, client, project name, completion date, outcome, status `active`/`withdrawn`, `created_at`/`updated_at`/`withdrawn_at`, with the `backfilled_projects_withdrawn_at` check keeping `status = 'active'` exactly when `withdrawn_at` is null; `employee_id` and `department_id` reference `employees` and `departments`, on delete restrict, so a department or employee named by any backfilled project can no longer be deleted), the `backfilled_projects_employee_id_idx` and `backfilled_projects_department_id_idx` indexes, the `backfilled_projects_guard` trigger (an insert is always active with database timestamps; a completion date after today in Asia/Dhaka is refused on insert and on any update that changes it; a withdrawn row never changes again; a withdrawal changes nothing but the status; `id`, `employee_id` and `created_at` are locked; withdrawing stamps `withdrawn_at`) and a `backfilled_projects_no_delete` trigger, both binding the service role too, plus RLS: select for the Administrator, a manager over the employee (`manages_employee`) and the employee themselves; insert and update for the employee themselves only (no Administrator or manager write policy); no delete policy. It also adds the read-only `public.department_options()` function (SECURITY DEFINER; every department's id and name only). This deliberately exposes every department's id and name — never its manager or parent — to any signed-in user, Staff included; anon cannot call it, which the staff portal's "Add a past project" form reads so Staff never read `departments`. No seed change. Every employee read (Administrator, manager and Staff) reads backfilled projects, so until this migration is applied those reads show "employee records unavailable"; the staff form says the department list is unavailable while `department_options()` is missing. Test rows can never be deleted (by design), so the live RLS test and the e2e spec reuse fixed throwaway employees and departments (BS-9160..BS-9183, "RLS Backfill slot …", BS-9192, "E2E Backfill").
- Manager archive and restore (Story 4.9): `20261014040000_manager_archive.sql` adds the `manager_set_employee_archived(text, boolean)` SECURITY DEFINER function (execute for `authenticated` only; anon and public revoked). A department manager archives or restores an employee in their subtree from the profile's **Account access** panel; the app calls the function through the manager's own JWT, never the service role. The function takes the actor from `auth.uid()`, re-checks scope (`manages_employee`), refuses the manager's own record and targets with equal or higher authority (Administrators, and managers of the caller's own department, a department the caller manages, or an ancestor of either), and writes the change and one `audit_events` row in one transaction. `set_employee_archived` (the Administrator path) is unchanged. Until it is applied, a manager's archive or restore reports "Accounts are temporarily unavailable. Nothing was changed." (PGRST202); Administrators and Staff are unaffected.
- Activity export (Stories 8.1-8.3): every export writes one `audit_events` row (action `export_activity`, the period) through a service-role-only function: `record_activity_export` (target = the Employee ID, single export by an Administrator or a department manager), `record_bulk_activity_export` (target `all-employees[+archived]`, the Administrator's bulk export) and, from `20261015050000_department_activity_export_audit.sql` (Story 8.3), `record_department_activity_export` (target `departments:<the manager's subtree department ids, sorted>[+archived]`, a department manager's bulk export). A manager's exports cover only their department subtree and never contain interview rows. Until the function an export needs is applied, that export shows the "could not be exported because a record source is unavailable" message and nothing downloads.
- Adding employees (Story 7.1): `20261015000000_employee_create.sql` adds two insert-only policies on `employees`: `employees_insert_admin` (an Administrator JWT, any department) and `employees_insert_managed` (a department in the caller's subtree, via `manages_department`). Both require a `department_id` and refuse a row that already carries `auth_user_id` or `archived_at`. No column, constraint or existing policy changes; `department_id` stays nullable at the column. No update or delete policy. The app adds employees through `employeesStore.create()` with the signed-in user's JWT (never the service role) and re-checks the department scope at the store. Until it is applied, "Add employee" reports "You can only add employees to your own department or its sub-departments." (RLS 42501) for everyone and nothing is added.
- Editing basic details (Story 7.2): `20261015010000_employee_details_update.sql` adds one SECURITY DEFINER function, `update_employee_details(employee_id, title, team, manager, office, employment_type)` (execute for `authenticated` only; revoked from `public` and `anon`). It lets the Administrator (JWT role) edit anyone and a department manager edit employees in their subtree (`manages_employee`), refuses Staff (even on their own record) and a caller whose own row is archived, validates the values (1–120 characters, employment type Permanent/Trainee/Intern) and updates only those five columns, so the department never changes here (only through a transfer). There is still no update policy on `employees`. The app calls it through `employeesStore.updateDetails()` with the signed-in user's JWT and re-checks the manager scope first. Until it is applied, saving details reports "Employee records are temporarily unavailable. Nothing was changed." (PGRST202) and nothing changes.
- Employment history (Story 7.3): `20261015020000_employment_history.sql` adds the `employment_history` table (role, employer, period, detail; `created_by`, `created_at`, `updated_at`, `removed_at`), its `employee_id` index, the `employment_history_guard` trigger (stamps the author and times, stamps `removed_at`, locks the employee/author/creation time, refuses a removal that also changes the entry, and makes removed rows immutable for every role, the service role included), a BEFORE DELETE trigger that refuses every delete (the service role's too), `truncate` revoked from the API roles plus a BEFORE TRUNCATE trigger, and select/insert/update policies for the Administrator, the employee themselves and a department manager of the employee's subtree (`manages_employee`). No delete policy. `db:seed` copies the fixture's employment history into it by fixed ids (`employmentHistorySeedId`), insert-only, so edits and removals survive a re-run. Every employee read now includes employment history, so until this migration is applied every profile read reports "Employee records are temporarily unavailable." (PGRST205), and until `db:seed` runs after it the demo employees show "No employment history has been recorded.". Because rows can never be deleted, an employee with employment history can no longer be deleted either (`ON DELETE RESTRICT`); archive it instead.
- Skills and evaluation (Story 7.4): `20261015030000_skills_and_evaluation.sql` adds `employee_skills` (a skill rated 1–5 with evidence; unique per employee by `lower(name)`, index `employee_skills_employee_name_key`) and `employee_evaluations` (one per employee: strengths, development priorities, readiness, reviewer, review date), each with three select-only policies (Administrator, the employee's own, `manages_employee`) and no insert, update or delete policy. Writes go only through two SECURITY DEFINER functions (execute for `authenticated` only; revoked from `public` and `anon`): `rate_employee_skill(employee_id, name, level, evidence)` (insert, or update the same skill name in any case) and `update_employee_evaluation(employee_id, strengths, development_priorities, readiness)` (upsert; the reviewer label "<name> · Administrator" / "<name> · Department manager" and the date, today in Asia/Dhaka, come from the session). Both allow the Administrator (anyone) and a department manager (their subtree), refuse Staff (even on their own record) and an archived caller, and validate the values. The app writes through `assessmentsStore.rateSkill()` / `saveEvaluation()` with the signed-in user's JWT and re-checks the manager scope first. `db:seed` then inserts the fixture's skills (skipping any whose employee and lower-cased name already exist) and evaluations (insert-only by employee), with `updated_by` null. Every employee read (directory, profile, staff page) reads these tables, so apply this migration before deploying the Story 7.4 code; until it is applied those reads show "Employee records are unavailable" (PGRST205) and saving reports "Skills and evaluations are temporarily unavailable. Nothing was changed." (PGRST202).
- Department transfer (Story 4.8): `20261016020000_department_transfer.sql` adds the nullable `audit_events.from_department_id` and `to_department_id` columns (no foreign keys, so audit rows outlive departments), widens `audit_events_action_check` to allow `transfer`, adds the `audit_events_transfer_check` check (a transfer row always has a destination; other rows have neither department), and adds the `transfer_employee(text, uuid)` SECURITY DEFINER function (execute for `authenticated` only; anon and public revoked). The Administrator or a department manager moves an employee from the profile's **Department** panel; the app calls the function through the actor's own JWT, never the service role. The function takes the actor from `auth.uid()`, requires the Administrator role or authority over both the source (`manages_employee`; an employee with no department can only be moved by the Administrator) and the destination (`manages_department`), refuses the current department and any employee with an open assignment, and writes the change and one `audit_events` row (action `transfer`, from, to) in one transaction. Past assignments keep their recorded department; training follows the employee. No seed change. Until it is applied, a transfer reports "Employee records are temporarily unavailable. Nothing was changed." (PGRST202); nothing else is affected. The live RLS test reuses fixed throwaway employees and departments (BS-8000..BS-8031, "RLS Transfer slot …"), because the assignments it creates can never be deleted.
- My record (Story 4.10): no migration and no RLS change. Department managers always get **My record** in the management portal (their own attendance, daily log, interviews, training, assignments and evaluations read-only, and past projects), read and written under the Staff own-record rules. An Administrator gets it only when their auth user id is set as `employees.auth_user_id` on exactly one non-archived employee row; set it with the service role or the Supabase SQL editor (for example `update employees set auth_user_id = '<admin auth user id>' where employee_id = 'BS-…';`). The link is looked up on every request; with no link, an archived row or a failed lookup, the Administrator simply has no My record.

## Publish and verify

1. Apply any pending migrations (`npm run db:push`) and seed if the table is new (`npm run db:seed`). On a fresh project, disable sign-ups and run `npm run db:seed-admin` once.
2. Run `npm run check` (includes the RLS integration test when Supabase variables are set) and `npm run test:e2e` before publishing changed application code.
3. Deploy the current source through the connected Vercel account. A CLI alternative is `npx vercel` after `npx vercel login`; use `--prod` for a production deployment.
4. Wait for successful deployment and capture the returned HTTPS URL.
5. Confirm unauthenticated visits show sign-in, an incorrect password, the retired `manager@example.com` credentials and the old shared staff password are rejected, the Administrator's named account opens the employee directory, and a provisioned Staff account opens only its own portal.
6. Refresh after sign-in to check session persistence, open an employee profile, verify filtering and sign out.

This is a demonstration with fictional records. Administrators and Staff have named accounts. An Administrator can archive and restore an employee's access from their profile (Story 1.4) and Staff attendance is persisted (Story 1.5); external integrations remain separate implementation work.
